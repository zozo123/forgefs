# ForgeFS supply chain: SBOM, reproducibility, dependency policy

This document records three things the release path must be able to prove, not
assert: what is in the binary, that the same source produces the same bytes,
and which dependencies are allowed to be there at all.

`docs/RELEASING.md` owns the release mechanics. This document owns the
evidence those mechanics produce.

## SBOM

### Tool choice

Every release target publishes a CycloneDX 1.5 JSON SBOM generated by
**`cargo-cyclonedx`, pinned to `0.5.9`** and installed with
`cargo install cargo-cyclonedx --version 0.5.9 --locked`.

The three candidates were judged against what this release job can actually
do:

| | `cargo-cyclonedx` | `cargo-sbom` | `syft` |
|---|---|---|---|
| Licence | Apache-2.0 | MIT | Apache-2.0 |
| Maintenance | the CycloneDX/OWASP organisation, alongside the specification itself | one maintainer | Anchore, actively maintained |
| Install inside the existing job | `cargo install --version --locked`, same mechanism already used for `cargo-audit` and `cargo-deny` | `cargo install --version --locked` | published as a prebuilt Go binary whose documented install path pipes a fetched script into a shell |
| Network at generation time | none beyond the registry fetch `cargo build --locked` already performs; the graph comes from the committed `Cargo.lock` | same | same, but it must be fetched first |
| Per-target dependency graph | `--target <triple>` resolves the graph exactly as cargo does for that triple | no target selection | infers from the built binary, not from the resolved graph |

`syft` is rejected on the install path: `.github/scripts/check-workflow-security.py`
forbids `curl`/`wget` in any workflow `run` step precisely so that release
tooling cannot arrive from an unpinned installer, and adding a Go toolchain to
four build runners to `go install` it is a larger trusted surface than the
SBOM is worth. `cargo-sbom` is a reasonable tool but has a single maintainer
and no `--target` selection, and ForgeFS ships four triples whose graphs are
not identical. `cargo-cyclonedx` is maintained by the same organisation as the
format, installs through the mechanism the release job already trusts, reads
the committed lockfile, and can be asked for one triple at a time.

Recorded so it is not mistaken for a gate: `cargo-cyclonedx` 0.5.9 warns about
crates whose `license` field uses the deprecated `MIT/Apache-2.0` slash form
and records those as named licences rather than SPDX expressions. The licence
*policy* authority is `deny.toml` via `cargo deny check licenses`, which
parses those crates correctly; the SBOM is an inventory, not the policy.

### What is published

`.github/scripts/release-sbom.sh` runs in each `build` matrix job, next to the
binary it describes, and produces one asset per target:

```
forge-<version>-<target>.cdx.json
```

It is a first-class release asset. It is listed in
`.github/scripts/release-assets.sh`, so `assemble` refuses a payload without
it; it is covered by `SHA256SUMS`; and because the attestation subject is that
checksum manifest, the SBOM is attested by `actions/attest-build-provenance`
exactly like the tarballs. It is not a side artifact.

Each SBOM is bound to its release context. `metadata.properties` carries
`forgefs:release:version`, `forgefs:release:commit`, `forgefs:release:target`
and `forgefs:release:rustc`, and `metadata.component` names the `forge`
binary.

### The SBOM is checked against the binary that ships

An SBOM that nobody compares to reality is a list of hopes. Release builds
embed crate source paths in panic locations, so the crates a binary actually
links can be recovered from the binary itself:

```
registry/src/<index>/<name>-<version>/...
```

`release-sbom.py verify-binary` recovers that set from
`target/<target>/release/forge` and fails the build if the SBOM does not list
any of them. It also fails if fewer than ten crate paths are recovered, so the
check cannot pass by finding nothing. On `x86_64-unknown-linux-gnu` at the
time of writing it recovered 26 crates against 112 SBOM components. Both figures track the resolved graph rather than the check itself -- #401 alone removed four crates from it by collapsing the duplicate `digest 0.10` tree -- so read current numbers from the release's own SBOM instead of this line.

To repeat the check yourself against a published release:

```bash
tar -xzf forge-<version>-<target>.tar.gz
tr -c '[:print:]' '\n' <forge-<version>-<target>/forge |
  grep -o 'registry/src/[^/]*/[^/]*/' |
  sed 's#registry/src/[^/]*/##; s#/$##' | sort -u
python3 - forge-<version>-<target>.cdx.json <<'PY'
import json, sys
document = json.load(open(sys.argv[1]))
for component in document["components"]:
    print(component["name"] + "-" + component["version"])
PY
```

Every name in the first list must appear in the second.

## Reproducible builds

### What is proved, and where

`.github/scripts/release-reproduce.sh` runs as the `reproduce` job on
`ubuntu-24.04` for `x86_64-unknown-linux-gnu`. It builds and packages the exact
release commit **twice**: once in the checkout, once in a second `git worktree`
at a different absolute path with its own empty target directory. Every file
the packaging step emits must be byte-identical, and `assemble` depends on the
job, so a release cannot publish if it fails.

Its evidence is published as `forge-<version>-<target>.REPRODUCE.txt`, listing
the digest of each compared file and a `result=` line.

Measured while developing this change, in a Debian 12 x86_64 sandbox with
the pinned rustc 1.97.0, all three packaged files matched:

```
identical a4eb9b2d…  forge-0.3.0-x86_64-unknown-linux-gnu.BUILD-INFO.txt
identical 6522da67…  forge-0.3.0-x86_64-unknown-linux-gnu.cdx.json
identical 1cfeaf8f…  forge-0.3.0-x86_64-unknown-linux-gnu.tar.gz
result=reproducible
```

The `forge` binary itself is reproducible independently of the packaging: two
clean `cargo build --release --locked -p forge-cli` runs in separate clones at
different absolute paths produced the identical binary. rustc does not leak
the build path into it.

### What had to change to get there

The previous packaging step was **not** reproducible, and the check above
fails against it — that is how the check was validated. `tar -czf` inherited
three things from the builder:

1. **mtimes.** Staged copies carried the packaging wall-clock time.
2. **owner.** The runner's uid/gid and user/group names were stored verbatim.
3. **member order.** Members were archived in directory-read order rather than
   a fixed order.

The gzip layer was already clean, because GNU `tar -z` compresses a stream and
therefore stores no name or timestamp.

`release-build.sh` now fixes all three: modes are set explicitly, mtimes are
set from the committer time of the release commit (rendered by `git` itself,
so no `date(1)` dialect is involved), members are listed in a fixed order with
`--no-recursion`, ownership is pinned to numeric 0/0, the archive is written as
`ustar`, and the stream is compressed with `gzip -9 -n`.

### What is *not* claimed

- **Only `x86_64-unknown-linux-gnu` is proved.** The other three targets are
  packaged by the same code with the same normalisation, but no double-build
  runs for them, so this document does not claim them. Adding a target to
  `reproduced_targets` in `release-assets.sh` without also running the proof
  for it would be a false claim.
- **Across different machines, `BUILD-INFO.txt` is expected to differ.** It
  records `uname -a`, the runner image, and the toolchain: it is environment
  evidence, deliberately, and it is only compared within a single job.
- **Across different operating systems, the compressed bytes are not claimed
  to match.** GNU `gzip` and the BSD `gzip` on macOS are different DEFLATE
  implementations. This never arises for a single target, because each target
  is built on one runner class, but it is the reason the claim is scoped per
  target rather than stated globally.
- **A different rustc produces a different binary.** The release pins
  `RELEASE_RUST`; reproducibility is a claim about that toolchain, and the
  exact `rustc` version is recorded in both `BUILD-INFO.txt` and the SBOM.

## Dependency policy

Enforced by the `supply-chain` job, on which `assemble`, `attest` and
`publish` all depend:

- `cargo audit --deny warnings` against the committed lockfile (RustSec), also
  scheduled weekly in `security.yml`;
- `cargo deny --locked check advisories bans licenses sources` against
  `deny.toml`: `yanked = "deny"` with an empty ignore list, a licence
  allow-list with no exceptions, and `unknown-registry`/`unknown-git` denied
  with an empty `allow-git`;
- `git diff --exit-code -- Cargo.lock`, so nothing in the release path may
  silently move the resolved graph;
- every release/security tool installed by exact version with `--locked`:
  `cargo-audit 0.22.2`, `cargo-deny 0.20.2`, `cargo-cyclonedx 0.5.9`.

Note the two deliberate non-gates, which carry their justification in
`deny.toml`: `[bans] wildcards` and `multiple-versions` are warnings.
